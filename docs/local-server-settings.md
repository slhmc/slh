# Настройки локального сервера

Дата: 31 октября 2026. Изменения выполнены поверх существующего незакоммиченного дерева; пользовательские серверы и аккаунты не использовались для тестирования.

## Причина и выбранная структура

Раньше общий `fieldset` блокировал форму вместе с переходами между подразделами, а ядро разрешало редактирование списков только после остановки. Блоки расположения и оформления стояли перед серверными параметрами, поэтому управление игроками требовало длинной прокрутки.

Выбран существующий экран настроек с двумя уровнями навигации: основные вкладки рабочей области и компактные подразделы внутри настроек. Это сохраняет знакомую композицию SLH и не добавляет ещё одно постоянное боковое меню. Существующие `ServerConfigFields`, `SettingRow`, `SettingGrid`, `SettingLayout`, `Toggle`, `Button`, `Dialog` и пиксельные иконки остаются основой. Новых цветов, размеров шрифта или токенов нет. Ближайшие аналоги — форма создания сервера, настройки сервера по умолчанию и настройки сборки.

Первым открывается «Игроки и доступ». Остальные подразделы: ядро и версия, Java и запуск, мир, сеть, правила сервера, дополнительные параметры. Вкладки доступны во всех состояниях сервера; блокируются только поля, которые нельзя безопасно применить без остановки. Переходы сохраняют несохранённый ввод, поддерживают стрелки, Home и End.

По уточнению пользователя положение вкладок и панелей меняется только в общих настройках лаунчера. Блок Server layout удалён, серверные страницы используют общие `instanceTabsPosition` и `instancePanelPosition`, старые серверные переопределения игнорируются без удаления из сохранённых данных. Ctrl-перенос главного меню для смены стороны удалён. Видимость и порядок вкладок по-прежнему доступны через их контекстное меню.

## Сопоставление с хостингами

- [Aternos: параметры сервера](https://support.aternos.org/hc/en-us/articles/360030513552-The-options-of-your-server-explained): параметры требуют перезапуска, управление игроками вынесено отдельно. В SLH это разделение показано доступностью конкретных полей и отдельным подразделом игроков.
- [BisectHosting: белый список](https://help.bisecthosting.com/hc/en-us/articles/40210472717211-How-to-Set-a-Whitelist-for-a-Minecraft-Server): управление через консольные команды. В SLH те же действия доступны через формы.
- [Apex: OP](https://apexminecrafthosting.com/guides/minecraft/control-panel/how-to-op-yourself/?translationUnavailable=1): команда `op` и отдельная настройка стандартного уровня прав. SLH не обещает произвольный уровень через команду работающего сервера.
- [Paper: стандартные списки](https://docs.papermc.io/paper/reference/vanilla-data-files/): работающие кешированные списки меняются командами, а не внешней записью JSON.

## Применение изменений

| Состояние | Игроки, OP, баны | Параметры запуска и server.properties |
| --- | --- | --- |
| Создан, остановлен, завершился с ошибкой; процесс не работает | Проверка ревизии и сохранение файлов с прежними полями | Редактирование и сохранение |
| Работает под управлением SLH | Стандартные команды и ожидание записанного сервером результата до 10 секунд | Чтение; редактирование после остановки |
| Запускается, останавливается, устанавливается, потеряно управление | Чтение и понятное объяснение недоступности | Чтение |

Включение белого списка на работающем сервере применяется сразу; на остановленном переключатель сохраняется вместе с параметрами. Ручной UUID и произвольный уровень OP доступны после остановки. При работе имя разрешает сам Minecraft, уровень OP берётся из стандартного параметра сервера. Плагины могут переопределять команды и хранить отдельные списки.

Отправка в stdin не считается подтверждением изменения: ядро проверяет файлы, записанные сервером. Если результат не появился, интерфейс предлагает обновить список и проверить консоль. Нет отката уже отправленной серверу команды и нет автоматического повторения. Проверки имени, IP и управляющих символов предотвращают добавление второй команды. Запись напрямую в живые JSON-списки не используется.

## Обновление 1 ноября: доступ во время запуска, мир и ручное ОЗУ

Это обновление заменяет прежнее ограничение состояния `starting` и прежнее описание памяти.

По снимку и read-only диагностике обнаружен запуск Horizon: Java-совместимый вывод ещё готовил мир, затем host перешёл в `running`. Теперь списки доступа используют актуальный `runtimeState` из ответа ядра, а не только копию состояния страницы. При возвращении в окно статус обновляется сразу. Поля белого списка, OP и банов доступны при запуске; подтверждённое действие ждёт готовности управляющего host до 180 секунд, затем отправляет команду. Во время ожидания прямой записи JSON нет. Пустой файл списка, который Minecraft создал во время запуска, не вызывает ложный конфликт; реальные изменения записей требуют обновления списка.

Новый подраздел «Управление миром» использует те же SettingRow, Button, Dialog и пиксельные иконки. Доступны сложность, режим по умолчанию, тайм-аут бездействия, время, погода, граница мира, сохранение мира и редактор gamerules. Есть популярные правила и ввод произвольного идентификатора с булевым или целочисленным значением. Команды проходят проверку параметров; вывод сервера показывается нейтрально, отправка не выдаётся за подтверждение изменения. Плагины могут заменить команду или отказать в ней.

Названия правил учитывают версию: например, `keepInventory` в старых версиях и `minecraft:keep_inventory` с 1.21.11. Распространение огня учитывает изменение типа: прежний `doFireTick` — boolean, новый `fire_spread_radius_around_player` — целый радиус. У PvP, командных блоков и Нижнего мира в современных версиях есть gamerules; устаревшие поля server.properties больше не показываются. Любое дополнительное поддерживаемое правило можно указать по идентификатору.

ОЗУ Java задаётся ручным вводом любых целых значений от 128 до 1048576 МиБ с проверкой `минимум ≤ максимум`. Пресетов и фиксированного набора значений нет. Отдельная кнопка сохраняет только два ключа профиля через JSON update в БД, не меняя `server.properties`, скрипты, текущий процесс или план работающего сервера. Новый диапазон используется при следующем запуске. Изменение работающей JVM на лету не обещается. В обзоре подпись — «Память ОЗУ (МиБ)». Horizon — нативное ядро без Xms/Xmx; в обзоре и боковой панели для него отображается автоматическое управление памятью вместо ложного диапазона Java.

Опрос скрытых подразделов останавливается. Общий Save по-прежнему относится к остановленным параметрам запуска и свойствам; live-команды и память имеют отдельные действия. Старые пользовательские файлы и существующее незакоммиченное дерево сохранены.

## Навигация настроек сервера

Настройки существующего сервера используют боковой список разделов по образцу настроек лаунчера. Четыре списка доступа переключаются внутри раздела; скрытые формы остаются смонтированными, поэтому незавершённый ввод сохраняется. Тип аккаунта вручную не выбирается: запрос отправляет `identityProvider: auto`, как предусмотрено ядром. Ограничения остановленного и работающего сервера не менялись.

Проверка в браузерном preview: EN/RU/DE, 800×560 и 1440×900, переходы клавиатурой, подтверждение и отмена, добавление и удаление, работающий и остановленный сервер. Сравнение выполнено с боковой навигацией настроек лаунчера; дополнительный ряд вкладок нужен для четырёх независимых списков. Проверка использовала изолированные фиктивные данные, не реальный сервер.

Проверки уточнения навигации и оформления (1 ноября): `check:ui` — 2040 значений, `npm run build`, 176 frontend-тестов, 11 тестов Rust-оболочки и 225 тестов ядра (5 ignored).
